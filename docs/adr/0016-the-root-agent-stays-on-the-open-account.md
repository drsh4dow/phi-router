# The root agent stays on the open account, and the router keeps sealed content

A request that is not pinned runs on the clean lane whatever its verdicts. Each sealed part reaches the open account as a stub that carries a handle, and the router keeps the part's content in the sealed store, one 0600 file per session beside the verdict store. The root agent hands work that needs PHI to the pinned subagent by naming handles. The router puts the content back only in a pinned request, or in a request the clean lane refused, and adds the pinned instructions, built from the policy, to a request on `phi/sealed` or with the pinned line. In Claude Code and pi-harness the subagent's last answer passes the answer check, with up to five rewrites, before the root agent receives it.

We chose this because the earlier lane rule, sealed new content runs on the sealed lane, sent the whole conversation to the BAA account on every request until new content cleared. The BAA account is billed per token, so each such request paid for the full context, and the task passed silently to another model mid-turn, which then wrote the report. The owner asked for this design on 2026-11-20, "pass the sealed message to a delegate that can open it and take it from there", and settled it on 2026-11-25 from his diagram.

## Considered options

- Keep the lane rule and make the stub carry a handle. Rejected because it keeps the cost and the silent hand-over.
- The router redacts every sealed part on its own with a BAA call. Rejected because it pays for parts the root agent never needs read, and adds a second mechanism beside the pinned subagent.
- The router runs the rewrite itself, holding back a pinned reply until it clears. Rejected because the turns it adds never reach the harness transcript, and a subagent that calls a tool mid-rewrite breaks the conversation. The harness runs the loop instead, from its hooks in Claude Code and from the phi-router package inside the delegate in pi-harness.
- Run the rewrite loop in Codex too. Rejected because the owner keeps Claude Code and pi-harness as the first-class harnesses: "the other harnesses gets an instruction in their SETUP about requiring the subagents systems and they setup that themselves". Codex opens handles for its `phi-sealed` subagent and has no answer check.
- Keep the sealed store in memory. Rejected because a handle must still open after compaction removes the original part from the transcript, and after a router restart.
- Encrypt the sealed store. Rejected because the harness transcripts on the same disk already hold the same text in plain form.

## Consequences

- The verdict store still never holds content. The sealed store does, and sits beside it. Nothing deletes either one, so sealed content stays on disk, 0600, until the user removes it.
- The root agent goes blind on a sealed tool result and must delegate to read it. A whole part seals, so one name in a long output hides all of it.
- The border is still the safety: an answer that passes the answer check is judged again as new content before it reaches an open account. In Codex, a sealed answer reaches the root agent as a stub with a handle, with no rewrite.
- The harness reaches the answer check at `POST /phi-router/answer-check` with the session, the subagent id and the last answer. The router answers `cleared`, `rewrite` with the attempt and the message, or `gave-up` with the withheld answer's handle and the reply the root agent receives. It counts rewrites per session and subagent in the sealed store, and `status` reports the pinned runs, the rewrites, each withheld answer and the key of each subagent's last cleared answer, which `/phi`, the turn-end notice and Claude Code's status line read.
- Claude Code checks the answer in four hooks of its plugin. `SubagentStop` on `^phi-router:phi-sealed$` exits 2 with the rewrite on stderr, which continues the subagent. In auto mode the subagent hands back through the `SubagentHandback` tool, and `PreToolUse` on `^SubagentHandback$` denies it with the rewrite or swaps its message for the reply. Neither hook can withhold an answer when the router fails, so the answer reaches the root agent only through a hook that fails closed: `PostToolUse` on `^Agent$` for a foreground subagent, and `UserPromptSubmit` for the `<task-notification>` prompt of a background subagent or a `SendMessage` continuation. Each lets the answer through only when `status` lists its key as cleared. Otherwise the tool result becomes the withheld answer's reply or a line saying phi-router could not check the answer, and the notification is blocked with that line as its reason.
- In pi-harness, a delegate on `phi/sealed` loads the phi-router package and carries the root agent's session in `PHI_ROUTER_SESSION`, so its requests reach the root's sealed store. The package checks the delegate's last answer before the delegate settles: a rewrite is a message that continues the delegate, and a withheld answer, or one the router could not check, is a context edit that replaces the answer in the delegate's session, where pi-harness reads it. Stock pi has no delegate, so there the session switches to `phi/sealed`.
- The BAA account still runs a whole session on `phi/sealed`, in a BAA repo, for a Codex title request, and on overflow, where it receives the same body with handles.
