# Verify the formal model

`tools/formal/` holds a TLA+ model of the router's design. TLC, the TLA+ model checker, walks every order of steps the model allows inside small bounds and checks the properties below in each state. A test checks the orders someone wrote down. The model checks crashes, retries, compactions, failover and two requests of one session racing, in every order.

## The properties

| Property                                                                                                                                                            | Invariants                                                                                                                                                                                                         | The harm when it breaks                                                                                                                                              |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| (a) An open account receives only cleared parts and stubs                                                                                                           | `NoSealedPartAtOpenAccount`, `NoUnjudgedPartAtOpenAccount` in `Route.tla`                                                                                                                                          | PHI reaches an account with no BAA.                                                                                                                                  |
| (b) A request with sealed new content never runs on the clean lane, and failover moves only from the clean lane to the sealed lane                                  | `SealedNewContentRunsSealed`, `FailoverOnlyToSealedLane`                                                                                                                                                           | The whole request, PHI included, goes to an open account.                                                                                                            |
| (c) A verdict never changes from sealed to cleared inside one policy version                                                                                        | `VerdictNeverUnseals`                                                                                                                                                                                              | A later request passes a sealed part through the border.                                                                                                             |
| (d) The router never exits while a registered instance is alive. Once no instance is alive it is eventually down, and within the lease interval in the model's time | `NeverExitsWhileRegistered` and `ExitsWithinLeaseInterval` (invariants), `ExitsAfterLastInstance` (temporal property, under fairness on the router's lease check, exit and the passing of time) in `Lifecycle.tla` | A live session loses its router, or a router outlives every session.                                                                                                 |
| (e) A pinned request never reaches an open account                                                                                                                  | `PinnedRequestRunsSealed`                                                                                                                                                                                          | A pin the user set does not hold.                                                                                                                                    |
| (f) Each account the walk stops at gets its own 401 resend, whichever step brought the request there                                                                | `ResendPerAccount` in `Route.tla`                                                                                                                                                                                  | A login folder that could answer after its login is made fit gets no second send, and the request fails over or fails.                                               |
| (g) Each send names the substitute exactly when it goes to a BAA account that lacks the target model, whichever step brought the request there                      | `SubstitutePerAccount` in `Route.tla`                                                                                                                                                                              | A BAA account runs a model it lacks and fails, or an account that carries the model runs the substitute and the developer gets another model than the one asked for. |
| (h) A send names the substitute only once the request was sent to every BAA account that carries the target model                                                   | `TargetModelFirst` in `Route.tla`                                                                                                                                                                                  | A healthy BAA account that carries the model loses the request to one that lacks it, and the developer gets another model than the one asked for.                    |

## Does the change touch the model?

Run this skill when the diff touches a file in the coverage table below, a `.tla` file, or a `.cfg` file. Also run it when a change alters a fact in "What the code must uphold", even from a file outside the table.

## Run the check

`bun run model` runs every configuration. `bun run check` leaves it out. CI's `model` workflow runs it on a pull request that touches a `.tla` or `.cfg` file, `tools/formal/` or a file in the coverage table, and on every push to main. Its path list copies the coverage table, so a row that names a new file adds that file to `.github/workflows/model.yml` in the same commit. It needs Java 11 or later on PATH and the pinned jar, which `bun install` downloads into `node_modules/.cache/tlaplus/` and checks against its sha256 in `tools/formal/tla2tools.ts`. The check itself makes no network call.

The test passes when:

- each configuration under `holds/` exits 0 and prints `Model checking completed. No error has been found.`
- each configuration under `breaks/` fails on the one rule it names. An `INVARIANT <X>` exits 12 with exactly one line `Error: Invariant <X> is violated.`. A `PROPERTY` exits 13 with `Error: Temporal properties were violated.`, which names no property, so such a configuration names one.

To see one configuration's full output and trace, run TLC from `tools/formal/`. Use a scratch folder for the temporary files:

```sh
cd tools/formal
java -XX:+UseParallelGC -Djava.io.tmpdir=/tmp/tlc-scratch -cp ../../node_modules/.cache/tlaplus/tla2tools-1.7.4.jar \
  tlc2.TLC -workers 1 -metadir /tmp/tlc-scratch -config breaks/Route.NoStub.cfg Route.tla
```

The module is the configuration's file name up to its first dot. Use `-workers 1` for a trace, because one worker finds the shortest one.

## Read the result

Read every result with the **statechart** skill. It turns a violation into its shortest path in plain words, and draws the states of a passing run.

When a `holds/` configuration fails, decide which side is wrong before you change anything:

- **A real bug.** Each step of the trace is something the code does, in the order the trace gives, and the last state is a harm the property table names. Replay the path against the code as a test, one step per action, using the coverage table. Fix the code, never the invariant.
- **A modeling error.** A step in the trace is something the code cannot do, such as two steps the code runs without an await between them shown with another action in between. Fix the model, and say in the PR which step was wrong and why.

When a `breaks/` configuration passes or names another invariant, the model no longer catches that bug. Find out why before you touch the configuration. A model change that makes a broken variant pass has probably weakened a rule.

Never weaken an invariant, lower a bound, or delete a `breaks/` configuration to get green.

## What the code must uphold

The model holds only while the code does these. A change that breaks one needs a model change first.

Route:

- A request judges every part with no stored verdict, history included, because the lane rule reads "A sealed part in the new content, or a part sealed during this request, sends it to the sealed lane", and the border stubs each part still unjudged. The judgments stay in memory until they are stored.
- Storing merges so a sealed verdict stays sealed.
- The verdict store has one writer, the router process. A second process that writes a session's file, such as a `pin` command, must go through the router or own another file, since the one-step merge is a lock inside one process.
- Each send to an account reads the verdict store once and builds the body from that read, on failover and on the second send of the reasoning resend too. The lane can move from clean to sealed at send time, never back. No vendor CLI runs between that read and the send: a login folder is made fit to send before the read.
- The border passes only cleared parts and stubs every other one.
- Failover happens only before the first byte, and past the last BAA account the request fails.
- A send to the same account again, on the reasoning resend or on a login folder's first 401, happens at most once each, before the first byte, from a fresh read of the store (`Resend`, `Rejected`). The 401 resend belongs to the account: a request that moves to another account finds that account's resend unspent.
- Each send names its model from the account it goes to: the target model on the clean lane and at a BAA account that carries it, the substitute at one that lacks it. No send carries the model of an earlier send.
- The sealed walk tries the BAA accounts that carry the request's target model before those that lack it, each in file order, whatever brought the request to the sealed lane.
- The verdict store survives a router crash. A new policy version comes with a new router process and retires every stored verdict.
- Each session has its own verdict store. A content key holds no session id, so no cache of verdicts may span two sessions.
- The pin is read once, when the request arrives. A pinned request judges nothing. Parts from a pinned stretch have no verdict and are judged after the unpin.
- The account lists are read once, when the request arrives, and the request walks only those to its end. An account added to `config.json` serves only later requests.

Lifecycle:

- A lease is a pid plus that process's start time.
- `start` returns only after the lease is stored. Registering twice changes nothing.
- The lease registry is stored on disk, and a launched router adopts it.
- The router checks its leases once per 5 s interval, and stops accepting in the same step that decides to exit. Its process then ends before the next interval. The router itself takes these steps without waiting on any harness, which is the fairness the model assumes. A check drops a lease only on a `ps` read that exited 0, parsed whole line by line with start times that name a real second, and lists `ps`'s own pid. Any other read keeps every lease, so the model's exit bound assumes `ps` reads the processes.
- A closing router holds the port, so a new router binds only after the old one exits.
- Every session-start source runs `start`, so an alive instance relaunches the router after a crash.

## Bounds and scope

| Configuration                 | Bounds                                                                                                                                  | Distinct states | Local wall time |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | --------------- | --------------- |
| `holds/Route.cfg`             | 2 sessions of 3 parts, 1 request each, 2 open accounts, 2 BAA accounts, the first lacking the target model, 1 new part, 2 history parts | 370,230         | about 20 s      |
| `holds/Route.SameSession.cfg` | 1 session, 2 requests at once, other bounds the same                                                                                    | 373,230         | about 5 s       |
| `holds/Lifecycle.cfg`         | 3 instances, no symmetry because TLC can miss a temporal violation under it                                                             | 2,100           | under 1 s       |

Retries, crashes and policy changes are unbounded. The harness and the judge are free: a request can carry any of its session's parts, and any judgment can answer sealed or cleared. The model leaves out the wire format, tool-call pairing, streaming after the first byte, the content of a part, and which account inside a lane serves a request.

## Add a broken variant

Each design step is one operator in its module, above the actions. To show that a property catches a bug:

1. Add the broken operator at the end of the module, with the same parameters and a one-line comment that says what it breaks.
2. Add `breaks/<Module>.<Name>.cfg`. Copy the constants of a `holds/` configuration, add `<Operator> <- <BrokenOperator>`, and name one `INVARIANT` or one `PROPERTY`. Leave out `SYMMETRY`.
3. Run `bun run model`. The new configuration must fail on that rule.

`breaks/Route.NoStub.cfg` must stay. The test asserts it exists.

## Update the model for an intended change

When a design change is intended, change the operator or action that stands for it, run `bun run model`, and read any trace with the **statechart** skill. Update the coverage table, the facts above and the bounds table in the same commit. When a new step has an await inside it, split it into two actions, so other requests can run between them.
